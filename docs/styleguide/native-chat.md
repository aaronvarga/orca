# Native chat typography and color

Read before changing anything under `src/renderer/src/components/native-chat/`. Core rules: [`docs/STYLEGUIDE.md`](../STYLEGUIDE.md). `pnpm lint` enforces the type scale, softened-foreground, and focus-ring rules below (`config/ast-grep/rules/native-chat-*.yml`).

## Chat type scale

The native chat uses these steps and no others. Never write an arbitrary size (`text-[13px]`) inside `components/native-chat/`.

| Step             | Default | Use it for                                                                                                 |
| ---------------- | ------- | ---------------------------------------------------------------------------------------------------------- |
| `text-sm`        | 13px    | Anything the user reads: message prose, tool and agent activity rows, card titles and bodies, the composer |
| `text-xs`        | 12px    | Labels, timestamps, counters, secondary lines under a row                                                  |
| `text-2xs`       | 11px    | Captions, attribution, uppercase category labels                                                           |
| `text-3xs`       | 10px    | Badges and mono pills                                                                                      |
| `text-chat-code` | 12px    | Code blocks, diffs, commands and tool output                                                               |

The chat root (`.native-chat-appearance`) redefines these steps from the Text size setting, so every tier scales together; `text-chat-code` follows the Code text size setting. `text-sm` is the Text size itself, on one line height for prose and list items (20px at 13px). The smaller steps, the spacing unit, icons, padding and row heights follow the UI size: the Text size, except 14px at the 13px default, so they keep their earlier sizes (spacing 4px).

- Use spacing-scale utilities (`size-3.5`, `min-h-6.5`, `pl-3.25`), not pixel lengths (`min-h-[26px]`), or the element stays fixed while the rest scales.
- Size an element with one of these utilities only: a CSS rule that sets `font-size` outside a layer silently overrides them.

## Text colour, hover and focus

- **Primary text on the chat canvas** uses `text-chat-foreground`, and `text-chat-foreground-strong` for titles, hover and emphasis; both follow the Contrast setting. Markdown bold and headings keep the surrounding text color and stand out by weight. Don't soften `text-foreground` by hand (`text-foreground/85`). `text-foreground` is for text on a lifted surface inside the chat.
- **Secondary text on the chat canvas** (transcript rows, notices, labels between messages) uses `text-chat-foreground-faint`. `text-muted-foreground` is for text on a lifted surface inside the chat: cards, menus, popovers and the docks above the composer.
- **Row hover** in the transcript is `hover:bg-accent/20`. Buttons, menu items and card controls use `hover:bg-accent`.
- **Focus rings:** full-width transcript rows use the inset ring (`focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-inset focus-visible:ring-ring`) so it isn't clipped by the scroll container; standalone controls use `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring`. Inside the chat `--ring` is `--chat-focus-ring`, which clears 3:1 on the canvas; don't lower its opacity.
- **Theme overrides:** plugin themes can set `--chat-bold-foreground`, `--chat-muted-foreground`, `--chat-inline-code`, `--chat-inline-code-foreground`, `--chat-code-block`, `--chat-selection` and `--chat-selection-foreground`. They feed `text-chat-foreground-faint`, `bg-chat-inline-code-surface`, `bg-chat-code-surface` and the chat root's `::selection`, so use those rather than reading the theme tokens directly.
- **Selection** inside the chat is the link hue mixed into the canvas (close to the system highlight), with selected text in the full foreground so every role stays 4.5:1. Don't add per-component `selection:` colors in transcript text.
- **State colours:** warnings use `text-chat-warning`; diff lines use `text-chat-diff-added` / `text-chat-diff-removed`; what the reader has not seen yet uses `text-chat-unread`. They are mixed toward the foreground so they pass text contrast in light and dark. Don't use raw palette colours (`text-yellow-500`) or the git decoration tokens for text on a tinted row.

## Chat composition

The chat uses adapted React components from [Beautiful UI](https://www.beautifului.dev/) under `components/native-chat/beautiful-ui/` (MIT; `resources/licenses/beautiful-ui/LICENSE.txt`). Orca owns transport, drafts, Markdown, disclosure persistence, and virtualized scrolling; these components own presentation.

- `PromptBar` keeps a full-width editor at least two lines tall above the leading actions and model/send controls, without remounting the editor. The composer, milestones panel and agent status strips share `bg-card`, `border-border`, `rounded-xl` and `shadow-xs`, including the expanded composer. Keep an 8px (`pt-2`) gap between separate docked cards; worker and MCP strips stay separate. Background work, milestones and the thread goal share an inset stack attached to the composer. Milestones start visible and collapsed and continue to generate while collapsed or hidden; the composer checklist button controls visibility. Remember docking, visibility, disclosure and the selected progress view per conversation across restarts.
- `ToolChips` starts collapsed. Tool-run summaries use compact spacing and `font-mono text-xs`, visually subordinate to the conversation prose. Explicit reader disclosure choices and requested diff reveals still win. Keep the chevron, icon, summary and outcome counts vertically centered. Expanded runs include confirmed changed-file chips with recorded line counts, overflow disclosure and expandable existing patches. Tool targets fill inset chips, and their leading icon reveals an expansion chevron on hover/open.
- `ThinkingState` uses a compact disclosure and an indented trace; the single live tail uses Beautiful UI's `LoadingState` pixel grid with a CSS-only reduced-motion fallback, the current activity and real turn clock. Turn headers show duration summaries only after settlement.
- `StreamingText` groups the response with its actual agent label and existing response actions. Do not manufacture sources or follow-up suggestions.
- `ApprovalCard` is a compact decision surface with option rows and an action footer. Long plan approvals can use the conversation width. Permission decisions remain inside `SecuritySurface`.
- Claude and Codex chat sessions show only marked session milestones in a collapsible section attached above the composer by default. The header can pin it to the right in panes at least 1000px wide; narrower panes keep the composer attachment while remembering the right-dock choice. Reserve the same right gutter for transcript and composer. Reuse `NativeChatComposerTabStrip` for the inset borders and stacked seams. Its compact header shows the current milestone, completion count and overall ETA; the expanded body scrolls within a bounded height. Write milestone titles and blocker reasons in STE80 style: plain words, an active verb and one main idea. Aim for 6–12 words while preserving necessary scope and names. Each milestone can reuse the task row disclosure to show one to three short Markdown bullets about scope, constraints or checks, one point per line. These notes do not have separate subtask states. Include exact work item IDs and known URLs from the conversation when relevant. Render known URLs as links. Keep these notes collapsed by default and generate them with the plan, without another agent call or work item lookup. Reuse task rows, preserve the session disclosure choice, and show preparing/save-error states without inventing progress. The Generate/Regenerate action uses an isolated read-only worker on the owning host, never a queued main-chat turn. A newer native plan supersedes an in-flight worker result. Completed batches remain in journal history; new substantial work starts a fresh active batch. Native events and generated snapshots own the generated `chat-scratch` Markdown; its preview is read-only. Unfinished milestones combine status and ETA in one chip, with the monospace time in a darker inset segment; the header retains a standalone overall ETA badge. The ETA estimates the AI agent’s own remaining execution and verification time, not human effort. Estimates refresh with plan updates; they are not countdowns. The owning host also reviews progress with the isolated worker after ordinary tool, question, root-turn and child-agent activity, coalescing updates and limiting reviews to about once per two minutes during active work. A settled turn still gets a trailing review. Failed reviews keep the last known plan and retry on later progress. Reviews preserve goal IDs and unfinished scope, include bounded child evidence, and are discarded after a context clear or newer native plan. Clearing the conversation resets milestones. The header totals sequential work and takes the longest duration within each explicitly independent parallel group; incomplete totals are marked with +. Show update age and recommend refresh after ten minutes. Blocked and waiting states explain their reason in the status chip tooltip and accessible text, without a separate note under the row. Keep questions and user answers in the chat; the milestones pane has no answer fields or question actions. Completed milestones compare their initial estimate with observed time inside root-agent running turns, excluding idle gaps and declared blockers; never invent timing for retrospective completion. Preserve measured completion samples for subsequent background-review calibration. Ordinary task details stay in the transcript.
- The milestones section includes an Agents tab with the existing host child-state model, observed timing bars on a common scale, available token/model/activity details and links to captured transcripts. Retain settled roster entries after live work disappears. Qualify live claims with parent connection freshness, and show unverifiable when evidence is unavailable. Bars show observed spans, never a completion percentage. Keep the selected tab when collapsing, hiding or reopening the section. Provider-dependent data can be absent; do not infer milestone completion from a child finishing.
- Claude task progress comes from successful `TaskCreate`, `TaskUpdate`, `TaskGet` and `TaskList` results, alongside legacy `TodoWrite` and Codex plans. The composer task list starts expanded; reader collapse choices persist while it updates.
- `TaskRows` groups the provider's actual tasks into bordered lists with status badges and numbered activity rings. Rows expand only when the provider supplies distinct active wording, an outcome, error or output path; do not invent subtasks or progress percentages. At narrow widths, status badges sit below labels. `CodeBlock` uses a language header, copy/wrap controls, and a numbered gutter when unwrapped; the gutter is excluded from copying.
- Preserve light/dark themes, chat text/code sizes, contrast settings, and the existing canonical tokens in every port. Do not copy gallery demo timers, data, browser portals, fonts, or shaders.

- Hand Off to Another Agent invokes the installed `handoff` skill in the source session and `handoff-resume` in the destination. Show preparation separately from launch and leave source approvals accessible. Wait for the exact briefing and its publication receipt under `.orca/handoffs/`; never select an automated transfer through the mutable `handoff.md` index. Keep retries on the same preparation request, preserve old briefings, and report missing skills or failed delivery without a transcript-only fallback. Skills remain usable outside Orca; plain-folder workspaces are supported.

- The shared progress dock also has an Output tab for session outputs, uploads and sources. Keep its selected view and dock choice per conversation. Reuse the same header, tabs and scroll region when pinned right or attached to the composer; the composer Output button opens that view directly. Index successful tool changes, observed search results and explicit attachments, never speculative file mentions. File links use the session host and existing file-open flow. Show a loaded-history qualification when older conversation messages are absent.

- In Output, reserve Outputs for explicitly linked documents, spreadsheets, presentations, images and media. Keep source code, configuration and line-specific citations in Links rather than Outputs. Keep other successful edits under a collapsed Changed files disclosure, using the same resource rows and count badge in both dock positions.

- Q&A shares the progress dock and saved selection. Show each structured question with its recorded user answer, preserving multi-select and free-text answers, cancellation, and unknown answers. Use journal receipts and explicit async reply identifiers or quotes; never guess from adjacent prose. Provide an earlier-history action when questions may be outside the loaded window. Keep Output links sent by the assistant separate from tool-observed Sources; accept local file links and safe HTTP(S) URLs through existing host-aware link actions.
